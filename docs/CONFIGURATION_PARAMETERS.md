# Подробное описание параметров конфигурации

## Секция Logging

### `Logging.LogLevel.Default: "Information"`
**Назначение:** Уровень логирования по умолчанию для всех категорий логирования в приложении.

**Описание:**
- Определяет минимальный уровень важности сообщений, которые будут записываться в лог
- Возможные значения (от менее к более важным):
  - `Trace` - самый подробный уровень, включает все сообщения
  - `Debug` - отладочная информация
  - `Information` - информационные сообщения (нормальная работа)
  - `Warning` - предупреждения
  - `Error` - ошибки
  - `Critical` - критические ошибки
  - `None` - логирование отключено

**Влияние на работу:**
- При `Information` записываются все события уровня Information и выше
- Более низкие уровни (Trace, Debug) будут игнорироваться
- Рекомендуется для production: баланс между информативностью и производительностью

**Примеры сообщений уровня Information:**
- `Monitoring cycle finished in 00:00:08.3566855 - processes: 114, leaks: 0, errors: 0`
- Успешное завершение цикла мониторинга

---

### `Logging.LogLevel.Microsoft.Hosting.Lifetime: "Information"`
**Назначение:** Уровень логирования для категории `Microsoft.Hosting.Lifetime`.

**Описание:**
- Специфичный уровень логирования для событий жизненного цикла приложения (Host)
- Переопределяет общий `Default` уровень для этой категории
- Категория отвечает за логирование событий запуска/остановки приложения

**Примеры сообщений:**
- `Application started. Press Ctrl+C to shut down.`
- `Application is shutting down...`
- `Hosting environment: Development`

**Влияние на работу:**
- Позволяет отслеживать жизненный цикл сервиса
- Важно для диагностики проблем запуска/остановки

## Секция MonitoringPipe

Конфигурация для межпроцессного взаимодействия между Service и UI через Named Pipes.

### `MonitoringPipe.PipeName: "MemoryLeakDetectorPipe"`
**Назначение:** Имя именованного канала (Named Pipe) для передачи данных мониторинга от Service к UI.

**Описание:**
- Имя создаваемого именованного канала в Windows
- Должно совпадать в конфигурации Service и UI
- Используется для связи между процессами `MemoryLeakDetector.Service` и `MemoryLeakDetector.UI`
- Named Pipe - это механизм IPC (Inter-Process Communication) в Windows

**Как работает:**
1. Service создает серверный Named Pipe с этим именем
2. UI подключается как клиент к этому каналу
3. Service отправляет результаты мониторинга через канал
4. UI получает данные в реальном времени

**Влияние на работу:**
- Если имена не совпадают - UI не сможет подключиться к Service
- Рекомендуется не менять без необходимости
- Должно быть уникальным, если запущено несколько экземпляров

---

### `MonitoringPipe.MaxServerConnections: 8`
**Назначение:** Максимальное количество одновременных подключений клиентов (UI-приложений) к серверу Named Pipe.

**Описание:**
- Ограничивает, сколько UI-приложений могут одновременно подключиться к Service
- Named Pipe сервер может обрабатывать несколько клиентов параллельно
- Каждое подключение создает отдельный поток для обработки

**Как работает:**
- Service создает Named Pipe сервер с указанным лимитом подключений
- При достижении лимита новые подключения будут отклоняться или ожидать освобождения слота
- Каждое UI-приложение - это один клиент

**Влияние на работу:**
- Значение 8 означает возможность подключения до 8 UI одновременно
- Увеличение значения увеличивает нагрузку на Service
- Уменьшение может привести к отказу в подключении при нескольких открытых UI

**Рекомендации:**
- Для обычного использования (1-2 UI) достаточно 4-8
- Для production с несколькими пользователями можно увеличить до 16-32

---

### `MonitoringPipe.ClientConnectTimeoutMs: 15000`
**Назначение:** Таймаут (в миллисекундах) для попытки подключения клиента (UI) к серверу Named Pipe.

**Описание:**
- Время ожидания успешного подключения UI к Service
- Если за указанное время подключение не установлено, считается неудачным
- Используется в UI-приложении при попытке подключения

**Как работает:**
1. UI пытается подключиться к Named Pipe серверу
2. Если Service не запущен или недоступен, UI ждет до таймаута
3. После таймаута попытка считается неудачной
4. UI будет пытаться переподключиться через `ReconnectDelayMilliseconds`

**Влияние на работу:**
- Слишком маленькое значение (например, 1000 мс) может привести к преждевременным отказам
- Слишком большое значение (например, 60000 мс) может заморозить UI при недоступном Service
- 15000 мс (15 секунд) - разумный баланс

**Рекомендации:**
- Для локального использования: 5000-15000 мс
- Для удаленного доступа: может потребоваться увеличение до 30000 мс

---

### `MonitoringPipe.ReconnectDelayMilliseconds: 2000`
**Назначение:** Задержка (в миллисекундах) перед повторной попыткой подключения после неудачной попытки.

**Описание:**
- Пауза между попытками переподключения UI к Service
- Используется в случае разрыва соединения или недоступности Service
- Предотвращает излишнюю нагрузку от постоянных попыток подключения

**Как работает:**
1. UI пытается подключиться (с таймаутом `ClientConnectTimeoutMs`)
2. Если подключение не удалось, UI ждет `ReconnectDelayMilliseconds`
3. Затем повторяет попытку
4. Цикл повторяется до успешного подключения

**Влияние на работу:**
- Слишком маленькое значение (например, 100 мс) создаст большую нагрузку
- Слишком большое значение (например, 10000 мс) задержит восстановление связи
- 2000 мс (2 секунды) - оптимальный баланс

**Рекомендации:**
- Рекомендуется: 1000-5000 мс
- Для быстрого восстановления связи можно уменьшить до 1000 мс
- Для экономии ресурсов можно увеличить до 5000 мс

---

## Секция Monitoring

Основные параметры алгоритма мониторинга и обнаружения утечек памяти.

### `Monitoring.PollingIntervalMilliseconds: 2000`
**Назначение:** Интервал (в миллисекундах) между циклами мониторинга процессов.

**Описание:**
- Определяет частоту сбора метрик всех процессов в системе
- Каждый цикл включает:
  - Сбор метрик всех процессов (Working Set, Virtual Memory, Handles, CPU, GC)
  - Обновление baseline для каждого процесса
  - Анализ на наличие утечек
  - Отправку результатов через Named Pipe

**Как работает:**
- Service запускает фоновый worker
- Каждые `PollingIntervalMilliseconds` выполняется цикл мониторинга
- Результаты накапливаются в истории и отправляются в UI

**Влияние на работу:**
- **Меньше значение (например, 500 мс):**
  - Более быстрая реакция на утечки
  - Выше нагрузка на CPU и диск
  - Больше данных в памяти
  - Больше шансов обнаружить кратковременные всплески
  
- **Больше значение (например, 5000 мс):**
  - Ниже нагрузка на систему
  - Медленнее обнаружение утечек
  - Меньше данных в памяти
  - Может пропустить быстротечные утечки

**Рекомендации:**
- **Для разработки/тестирования:** 1000-2000 мс (быстрое обнаружение)
- **Для production:** 2000-5000 мс (баланс производительности и точности)
- **Для долгосрочного мониторинга:** 5000-10000 мс (минимум нагрузки)

**Пример:**
- При значении 2000 мс: 30 циклов в минуту, 1800 циклов в час
- Для процесса с утечкой 10 MB/цикл: обнаружение через 4 цикла (8 секунд) при пороге 50 MB

---

### `Monitoring.BaselineWindow: 120`
**Назначение:** Количество последних сэмплов метрик, хранимых для расчета baseline (базовой линии) процесса.

**Описание:**
- Baseline - это "нормальное" состояние процесса в памяти
- Используется для сравнения текущих значений с эталоном
- Хранится очередь последних `BaselineWindow` измерений для каждого процесса

**Как работает:**
1. При каждом цикле мониторинга собираются метрики процесса
2. Значения добавляются в очередь размером `BaselineWindow`
3. При переполнении старые значения удаляются (FIFO)
4. На основе этих значений вычисляются:
   - Среднее значение (Average)
   - Медианное значение (Median, если `UseMedianForBaseline: true`)
   - Тренд роста (если `EnableTrendAnalysis: true`)

**Влияние на работу:**
- **Меньше значение (например, 30):**
  - Быстрее адаптируется к изменениям в работе процесса
  - Может быть менее устойчивым к кратковременным всплескам
  - Требует меньше памяти
  - Быстрее реагирует на изменения baseline
  
- **Больше значение (например, 300):**
  - Более стабильный baseline
  - Медленнее адаптируется к новому "нормальному" состоянию
  - Требует больше памяти
  - Лучше фильтрует кратковременные всплески

**Расчет:**
- При `PollingIntervalMilliseconds: 2000` и `BaselineWindow: 120`:
  - Baseline строится за: 120 × 2 сек = 240 секунд (4 минуты)
  - Хранится история за последние 4 минуты для каждого процесса

**Рекомендации:**
- **Для быстрого обнаружения:** 60-120 сэмплов (2-4 минуты при интервале 2 сек)
- **Для стабильности:** 120-240 сэмплов (4-8 минут)
- **Для долгосрочного анализа:** 240-600 сэмплов (8-20 минут)

---

### `Monitoring.WorkingSetLeakThresholdPercent: 15.0`
**Назначение:** Пороговое значение процентного роста Working Set памяти (в процентах) для обнаружения утечки.

**Описание:**
- Working Set - это физическая память, используемая процессом в данный момент
- Если текущий Working Set превышает baseline на указанный процент, это признак утечки
- Используется в комбинации с `WorkingSetLeakThresholdMb` для более точного обнаружения

**Формула расчета:**
```
Рост (%) = ((Текущий Working Set - Baseline Working Set) / Baseline Working Set) × 100%
Утечка = Рост ≥ WorkingSetLeakThresholdPercent И Рост в MB ≥ WorkingSetLeakThresholdMb × 0.5
ИЛИ
Утечка = Рост в MB ≥ WorkingSetLeakThresholdMb
```

**Примеры:**
- Baseline: 100 MB, Текущий: 115 MB → Рост: 15% → **Обнаружена утечка** (если рост ≥ 25 MB)
- Baseline: 100 MB, Текущий: 120 MB → Рост: 20% → **Обнаружена утечка** (если рост ≥ 25 MB)
- Baseline: 100 MB, Текущий: 110 MB → Рост: 10% → Утечка не обнаружена

**Влияние на работу:**
- **Меньше значение (например, 10%):**
  - Более чувствительное обнаружение утечек
  - Больше false positives (ложных срабатываний)
  - Быстрее обнаружение медленных утечек
  
- **Больше значение (например, 25%):**
  - Меньше false positives
  - Более надежное обнаружение
  - Может пропустить небольшие утечки
  - Позже обнаружение утечек

**Рекомендации:**
- **Для строгого обнаружения:** 10-15% (для production с высокими требованиями)
- **Сбалансированное:** 15-20% (рекомендуется)
- **Для снижения false positives:** 20-30% (для стабильных систем)

---

### `Monitoring.WorkingSetLeakThresholdMb: 50.0`
**Назначение:** Пороговое значение абсолютного роста Working Set памяти (в мегабайтах) для обнаружения утечки.

**Описание:**
- Абсолютное значение роста памяти, независимо от процентного роста
- Используется для обнаружения утечек в процессах с маленьким baseline
- Работает в комбинации с процентным порогом

**Примеры:**
- Baseline: 10 MB, Рост: 50 MB → Текущий: 60 MB → **Обнаружена утечка** (абсолютный порог)
- Baseline: 1000 MB, Рост: 50 MB → Рост: 5% → Может не быть обнаружена (если процентный порог 15%)
- Baseline: 200 MB, Рост: 50 MB → Рост: 25% → **Обнаружена утечка** (процентный порог)

**Влияние на работу:**
- **Меньше значение (например, 20 MB):**
  - Быстрее обнаружение утечек в малых процессах
  - Больше false positives для процессов с нестабильным потреблением памяти
  - Быстрее обнаружение медленных утечек
  
- **Больше значение (например, 100 MB):**
  - Меньше false positives
  - Позже обнаружение утечек (особенно в малых процессах)
  - Более стабильное обнаружение

**Рекомендации:**
- **Для раннего обнаружения:** 20-50 MB
- **Сбалансированное:** 50-100 MB (рекомендуется)
- **Для снижения false positives:** 100-200 MB

**Особенности:**
- Для процессов с baseline < 100 MB абсолютный порог более важен
- Для процессов с baseline > 500 MB процентный порог более важен

---

### `Monitoring.VirtualMemoryLeakThresholdPercent: 20.0`
**Назначение:** Пороговое значение процентного роста виртуальной памяти (в процентах) для обнаружения утечки.

**Описание:**
- Virtual Memory (виртуальная память) - это полный объем адресного пространства процесса
- Включает физическую память (Working Set) и память на диске (page file)
- Виртуальная память может расти даже когда физическая память стабильна

**Зачем отслеживать Virtual Memory:**
- Некоторые утечки проявляются в росте виртуальной памяти раньше, чем в Working Set
- Утечки виртуальных адресов (например, неправильное выделение памяти)
- Memory-mapped файлы, которые могут расти

**Примеры:**
- Baseline: 500 MB, Текущий: 600 MB → Рост: 20% → **Обнаружена утечка**
- Baseline: 500 MB, Текущий: 550 MB → Рост: 10% → Утечка не обнаружена

**Влияние на работу:**
- **Меньше значение (например, 15%):**
  - Более чувствительное обнаружение
  - Больше false positives (виртуальная память может колебаться)
  
- **Больше значение (например, 30%):**
  - Меньше false positives
  - Более надежное обнаружение

**Рекомендации:**
- Обычно на 5-10% выше, чем `WorkingSetLeakThresholdPercent`
- Рекомендуется: 20-30%

**Особенности:**
- Виртуальная память может быть менее стабильной, чем Working Set
- Поэтому порог обычно выше

---

### `Monitoring.HandleLeakThresholdPercent: 25.0`
**Назначение:** Пороговое значение процентного роста количества handles (в процентах) для обнаружения утечки.

**Описание:**
- Handles (дескрипторы) - это ссылки на системные ресурсы Windows (файлы, окна, мьютексы, таймеры и т.д.)
- Handle leak происходит, когда процессы не освобождают handles после использования
- Очень опасный тип утечки, так как может привести к исчерпанию системных ресурсов

**Типы handle leaks:**
- Утечки файловых handles
- Утечки таймеров (Timer leaks)
- Утечки оконных handles (в GUI приложениях)
- Утечки сокетов
- Утечки мьютексов/семафоров

**Примеры:**
- Baseline: 100 handles, Текущий: 125 handles → Рост: 25% → **Обнаружена утечка**
- Baseline: 50 handles, Рост: 20 handles → Рост: 40% → **Обнаружена утечка** (если абсолютный рост ≥ 20)

**Влияние на работу:**
- **Меньше значение (например, 15%):**
  - Быстрее обнаружение утечек handles
  - Больше false positives (handles могут колебаться)
  
- **Больше значение (например, 40%):**
  - Меньше false positives
  - Позже обнаружение утечек

**Рекомендации:**
- Обычно выше, чем пороги для памяти (handles более стабильны)
- Рекомендуется: 25-40%

**Особенности:**
- Алгоритм также использует абсолютный порог (минимум 20 handles роста)
- Это позволяет обнаруживать утечки в процессах с малым baseline (например, таймеры)

---

### `Monitoring.MinSamplesForLeakDetection: 5`
**Назначение:** Минимальное количество сэмплов метрик, необходимое для начала обнаружения утечек.

**Описание:**
- Перед началом анализа утечек необходимо накопить достаточное количество измерений
- Это необходимо для построения надежного baseline
- Процессы с недостаточным количеством сэмплов пропускаются в анализе

**Как работает:**
1. При первом обнаружении процесса начинается сбор метрик
2. Метрики накапливаются в baseline
3. Пока количество сэмплов < `MinSamplesForLeakDetection`, утечки не обнаруживаются
4. После накопления достаточного количества сэмплов начинается анализ

**Расчет времени до начала обнаружения:**
- При `PollingIntervalMilliseconds: 2000` и `MinSamplesForLeakDetection: 5`:
  - Время: 5 × 2 сек = 10 секунд после запуска процесса

**Влияние на работу:**
- **Меньше значение (например, 3):**
  - Быстрее начало обнаружения утечек
  - Baseline может быть менее точным
  - Больше вероятность false positives
  
- **Больше значение (например, 10):**
  - Более стабильный baseline
  - Позже начало обнаружения
  - Меньше false positives

**Рекомендации:**
- **Минимум:** 3 сэмпла (для быстрого обнаружения)
- **Рекомендуется:** 5-7 сэмплов (баланс)
- **Для стабильности:** 7-10 сэмплов

**Особенности:**
- Для долгоживущих процессов это значение не критично
- Для кратковременных процессов может потребоваться уменьшение

---

### `Monitoring.IncludeSystemProcesses: false`
**Назначение:** Включать ли системные процессы Windows в мониторинг.

**Описание:**
- Системные процессы (System, Idle, Session 0 процессы) обычно имеют нестабильное потребление памяти
- Они не являются пользовательскими приложениями и их утечки обычно не критичны для пользователя
- Исключение их из мониторинга снижает шум в отчетах

**Какие процессы считаются системными:**
- Процессы с `SessionId == 0` (служебные процессы)
- Процесс `System`
- Процесс `Idle`

**Влияние на работу:**
- **`false` (рекомендуется):**
  - Фокус на пользовательских приложениях
  - Меньше false positives
  - Более чистые отчеты
  - Меньше нагрузки на систему
  
- **`true`:**
  - Мониторинг всех процессов включая системные
  - Может быть полезно для системных администраторов
  - Больше данных и нагрузка

**Рекомендации:**
- Обычно оставлять `false` для обычного использования
- Установить `true` только при необходимости мониторинга системных процессов

---

### `Monitoring.LeakConfirmationCycles: 2`
**Назначение:** Количество последовательных циклов мониторинга, в которых должно быть обнаружено превышение порога для подтверждения утечки.

**Описание:**
- Механизм защиты от false positives (ложных срабатываний)
- Утечка подтверждается только если она обнаружена в N последовательных циклах
- Это фильтрует кратковременные всплески памяти

**Как работает:**
1. В цикле 1: обнаружено превышение порога → подозрение регистрируется
2. В цикле 2: превышение порога подтверждено → утечка фиксируется
3. Если в любом цикле порог не превышен → подозрение сбрасывается

**Влияние на работу:**
- **`1` (немедленное обнаружение):**
  - Самое быстрое обнаружение утечек
  - Больше false positives
  - Подходит для тестирования
  
- **`2` (рекомендуется):**
  - Баланс между скоростью и точностью
  - Фильтрует большинство кратковременных всплесков
  - Утечка подтверждается через 4 секунды (при интервале 2 сек)
  
- **`3` и более:**
  - Максимальная точность
  - Меньше false positives
  - Позже обнаружение утечек

**Пример:**
- `PollingIntervalMilliseconds: 2000`, `LeakConfirmationCycles: 2`
- Утечка обнаружена в 10:00:00 → подозрение
- Утечка подтверждена в 10:00:02 → фиксация утечки
- Общее время обнаружения: 4 секунды

**Рекомендации:**
- **Для разработки/тестирования:** 1-2 цикла
- **Для production:** 2-3 цикла (рекомендуется)
- **Для максимальной стабильности:** 3-5 циклов

### `Monitoring.UseMedianForBaseline: true`
**Назначение:** Использовать медиану вместо среднего арифметического для расчета baseline.

**Описание:**
- **Медиана** - среднее значение в отсортированном списке (более устойчива к выбросам)
- **Среднее** - сумма всех значений, деленная на количество (чувствительно к выбросам)

**Пример разницы:**
- Значения: [10, 12, 13, 14, 15, 16, 100]
- Среднее: (10+12+13+14+15+16+100) / 7 = **20.0** (влияет выброс 100)
- Медиана: **14** (среднее значение в отсортированном списке)

**Влияние на работу:**
- **`true` (рекомендуется):**
  - Более устойчивый baseline к кратковременным всплескам
  - Меньше false positives
  - Лучше для процессов с нестабильным потреблением памяти
  - Медленнее адаптируется к постепенным изменениям
  
- **`false`:**
  - Более чувствительный baseline
  - Быстрее адаптируется к изменениям
  - Больше false positives при кратковременных всплесках

**Когда использовать:**
- **Медиана (`true`):** Для большинства случаев, особенно когда процессы могут иметь всплески памяти
- **Среднее (`false`):** Для стабильных процессов с предсказуемым потреблением памяти

**Рекомендации:**
- Рекомендуется оставлять `true` для большинства случаев

### `Monitoring.EnableTrendAnalysis: true`
**Назначение:** Включить трендовый анализ для обнаружения постепенных утечек памяти.

**Описание:**
- Трендовый анализ использует линейную регрессию для выявления устойчивого роста памяти
- Позволяет обнаруживать медленные утечки, которые могут не превышать пороговые значения сразу
- Вычисляет скорость роста памяти (MB за цикл мониторинга)

**Как работает:**
1. Собираются последние N измерений Working Set
2. Вычисляется линейная регрессия (нахождение линии тренда)
3. Определяется наклон линии (slope) - скорость роста
4. Если тренд > 10 MB/цикл → утечка подтверждается даже без превышения порогов

**Примеры:**
- Цикл 1: 100 MB
- Цикл 2: 105 MB (+5 MB)
- Цикл 3: 110 MB (+5 MB)
- Цикл 4: 115 MB (+5 MB)
- Тренд: +5 MB/цикл → может быть обнаружен как постепенная утечка

**Влияние на работу:**
- **`true` (рекомендуется):**
  - Обнаружение медленных утечек
  - Раннее предупреждение о постепенных проблемах
  - Небольшая дополнительная нагрузка на CPU
  
- **`false`:**
  - Меньше нагрузки на CPU
  - Может пропустить медленные утечки
  - Обнаружение только быстрых утечек

**Рекомендации:**
- Рекомендуется оставлять `true` для большинства случаев
- Можно отключить только если нагрузка на CPU критична

**Особенности:**
- Требует минимум 3 сэмпла для работы
- Используется в дополнение к пороговому анализу, а не вместо него
